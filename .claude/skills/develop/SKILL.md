# /develop 개발 하네스

입력: `$ARGUMENTS`

아래 단계를 **순서대로** 진행한다. 각 단계에 들어갈 때 `## [단계 N] 이름` 형식으로 현재 단계를 사용자에게 한 줄로 알린다.

```
요구사항 입력
  → [멀티 에이전트 설계] 요구사항 분석 ∥ 엣지 케이스 분석 (소규모 기능이면 생략하고 메인이 직접 분석)
  → 설계 취합
  → 질문할 사항이 있는가? ─ 예 → 개발자에게 질문 → (피드백 반영) → 설계 취합으로 복귀 (범위가 바뀌면 기존 에이전트에 SendMessage)
                          └ 아니오 ↓
  → 핵심 코드 작성 및 설계 문서 생성
  → 설계 문서 승인/반려 ─ 반려 → (개발자 피드백) → 설계 문서 재생성 → 다시 승인/반려
                        └ 승인 ↓
  → 코드 구현
  → 검증 및 리뷰
  → P 단계 결과 보고
```

---

## [단계 1] 요구사항 입력

1. `$ARGUMENTS`가 비어 있으면 요구사항을 입력해 달라고 요청하고 멈춘다.
2. `$ARGUMENTS`가 존재하는 파일 경로(상대 경로는 프로젝트 루트 기준)이면 Read로 읽어 요구사항 원문으로 쓴다.
3. 그 외에는 입력 텍스트 자체를 요구사항 원문으로 쓴다.
4. 기능을 나타내는 짧은 영문 kebab-case `slug`를 정한다(예: `order-cancel`). 설계 문서 경로는 `.harness/<YYYY-MM-DD>-<slug>.md`이다.

## [단계 2] 멀티 에이전트 설계 (병렬)

**소규모 기능이면 이 단계를 생략한다.** 아래를 모두 만족하면 소규모로 본다.

- 한 패키지(api, web, shared 중 하나) 안의 변경이다
- 새 API(라우트, 요청·응답 타입)가 없다
- 새로 정하거나 바꾸는 비즈니스 규칙이 없다
- 예상 변경 파일이 3개 이하이다

생략할 때는 "소규모로 판단해 분석 에이전트를 생략합니다"라고 한 줄 알린다. 그다음 메인 에이전트가 두 에이전트의 출력 형식에 해당하는 내용(기능 명세, 엣지 케이스, 가정, 도메인 지식 후보, 질문)을 직접 정리하고 [단계 3]으로 간다. 개발자가 전체 분석을 요청하면 생략하지 않고 아래대로 진행한다.

**한 메시지에서** 두 서브에이전트를 동시에 실행한다. 두 에이전트에게 같은 입력을 준다.

- 요구사항 원문
- 지금까지 개발자에게 받은 답변과 피드백 전체 (첫 회차에는 없음)

| 에이전트               | 역할                                                                       |
| ---------------------- | -------------------------------------------------------------------------- |
| `requirements-analyst` | 기능 요구사항, 영향 범위(api/web/shared), 도메인 모델, API 계약, 구현 단위 |
| `edge-case-analyst`    | 경계값, 예외 흐름, 동시성, 권한, 데이터 정합성, 실패 시나리오              |

두 에이전트 모두 관련 `docs/domain/` 문서를 읽고, 새로 정해지는 비즈니스 규칙을 `도메인 지식 후보`로 낸다.

## [단계 3] 설계 취합

메인 에이전트가 두 결과를 하나의 설계안으로 합친다.

- 두 분석이 충돌하면 어느 쪽을 택했는지와 그 이유를 기록한다.
- 엣지 케이스마다 처리 방식(검증, 예외, 무시 등)을 정한다. 테스트로 연결하는 것은 backend-testing 1절 기준(깨지면 비즈니스 규칙이 깨지는 것)을 통과한 케이스뿐이다. 프레임워크가 처리하는 입력 형식 오류처럼 기준을 통과하지 못한 케이스는 처리 방식만 적고 테스트를 만들지 않는다.
- 두 에이전트가 낸 `개발자에게 물어볼 질문`을 모으고, 중복을 제거한 뒤 아래 기준으로 거른다.
  - **질문으로 남긴다**: 답에 따라 설계가 달라지고, 코드·규칙·관례로 결정할 수 없는 것 (비즈니스 정책, 범위, 우선순위 등)
  - **질문하지 않는다**: 합리적인 기본값이 있는 것. 이런 것은 가정으로 정하고 설계 문서의 `가정` 절에 적는다.
- 두 에이전트가 낸 `도메인 지식 후보`를 모아 중복을 제거한다.
  - 개발자 답변으로 정해진 규칙과 가정 중 비즈니스 정책인 것도 후보에 넣는다.
  - 기존 `docs/domain/` 문서와 **충돌**하는 후보는 기존 규칙을 바꿀지 개발자에게 묻는 질문으로 올린다. 임의로 가정하지 않는다.

## [단계 4] 질문할 사항이 있는가?

- **예** → AskUserQuestion으로 개발자에게 묻는다.
  - 한 번에 최대 5개까지 묻는다. 질문마다 선택지를 2~4개 두고, 추천안이 있으면 첫 번째에 두고 `(추천)`을 붙인다.
  - 답을 받으면 피드백 기록에 추가하고, **분석 에이전트를 새로 띄우지 않고** 메인 에이전트가 답을 설계안에 직접 반영해 [단계 3]부터 다시 진행한다.
  - 답이 범위를 바꾸는 경우(새 기능, 새로 영향받는 패키지, 새 API)에만 재분석을 맡긴다. 이때는 [단계 2]에서 띄운 에이전트 중 영향받는 쪽에만 **SendMessage로 답변과 다시 볼 범위만** 보낸다. 그 에이전트는 이미 읽은 파일과 분석 맥락을 갖고 있다. SendMessage를 쓸 수 없을 때만 새로 띄우고, 이때는 요구사항 원문과 피드백 전체를 함께 넘긴다.
  - 같은 질문을 다시 하지 않는다. 이 루프는 최대 3회까지 돈다. 3회가 지나도 질문이 남으면 가정으로 정하고 진행한다.
- **아니오** → [단계 5]로 간다.

## [단계 5] 핵심 코드 작성 및 설계 문서 생성

`.claude/skills/develop/templates/design-doc.md` 템플릿에 맞춰 `.harness/<YYYY-MM-DD>-<slug>.md`를 작성한다.

- **핵심 코드**는 실제 파일에 쓰지 않고 설계 문서 안의 코드 블록으로 작성한다. 여기에는 `@pomodoro/shared` 요청·응답 타입, 도메인 엔티티와 메서드 시그니처, Controller 라우트 시그니처, 주요 컴포넌트·Hook 시그니처가 들어간다. 승인 전에는 프로덕션 코드를 건드리지 않는다.
- 핵심 코드는 `.claude/rules/backend-conventions.md`, `.claude/rules/backend-testing.md`, `.claude/rules/frontend-conventions.md`를 따라야 한다. 예를 들어 현재 시각·난수는 주입받고, 공유 타입은 `@pomodoro/shared`에 둔다.
- 테스트 계획은 backend-testing 1절(무엇을, 어느 계층에서)에 맞추고, `it` 문장마다 "깨지면 어떤 규칙이 깨지는가"를 함께 적는다. 모든 계층을 채우지 않는다. 같은 규칙은 가장 낮은 계층에서 한 번만 검증한다.
- 필요한 의존성 추가(예: Jest, ORM)가 있으면 문서의 `의존성 변경` 절에 명시한다. 승인을 받아야만 설치할 수 있다.
- 정리한 도메인 지식 후보를 문서의 `도메인 지식 변경` 절에 `신규`/`수정`으로 적는다. 어느 문서의 어느 절에 무엇을 추가·수정할지 문장 그대로 쓰고, 수정은 `전 → 후`로 쓴다. 이 기능이 따르는 기존 규칙도 `참고`로 한 줄씩 적는다. 승인 전에는 `docs/`를 건드리지 않는다.

## [단계 6] 설계 문서 승인/반려

설계 문서 경로와 핵심 요약(5줄 이내)을 보여준 뒤 AskUserQuestion으로 묻는다.

- 선택지: `승인`, `반려 (피드백 입력)`
- **승인** → 문서 상단 `상태`를 `승인됨`으로 바꾸고 [단계 7]로 간다.
- **반려** → 개발자의 피드백을 받는다(선택지를 고르면서 Other로 적을 수 있고, 없으면 다시 묻는다). 피드백을 반영해 **설계 문서를 다시 생성**하고, 문서 하단 `변경 이력`에 회차와 피드백 요약을 남긴 뒤 [단계 6]을 반복한다.
  - 피드백이 요구사항 자체를 바꾸는 수준이면(범위 변경, 새 기능) [단계 4]의 재분석 규칙대로 기존 에이전트에 SendMessage로 재분석을 맡긴 뒤 [단계 3]부터 다시 진행한다.

## [단계 7] 코드 구현

먼저 메인 에이전트가 설계 문서의 `도메인 지식 변경`을 `docs/domain/`에 반영한다. implementer가 최신 규칙을 읽고 구현하게 하기 위해서다.

- 기존 문서는 해당 절에 내용을 추가하거나 고친다. 바뀐 규칙은 지우고 새 규칙으로 바꾼다(이력은 설계 문서에 남는다).
- 새 도메인이면 `.claude/skills/develop/templates/domain-doc.md` 템플릿으로 `docs/domain/<도메인>.md`를 만들고, `CLAUDE.md`의 `도메인 지식` 목록에 한 줄을 추가한다.

그다음 `implementer` 서브에이전트에 승인된 설계 문서 경로를 넘겨 구현을 맡긴다.

- api와 web의 변경이 서로 독립적이고 규모가 크면 `implementer`를 api용과 web용으로 나눠 병렬로 실행할 수 있다. 이때 `packages/shared` 변경은 먼저 한 번만 수행한다.
- implementer는 설계 문서 밖의 변경을 하지 않는다. 설계와 달라져야 하면 그 내용을 결과에 `설계 이탈`로 보고한다.

## [단계 8] 검증 및 리뷰

1. 메인 에이전트가 `bash .claude/skills/develop/scripts/verify.sh`를 한 번 실행한다. pnpm 명령을 하나씩 따로 실행하지 않는다.
   - 스크립트는 shared build → `pnpm build`(타입 검증) → `pnpm test` → `pnpm lint` → `pnpm format:check`를 차례로 돌린다. 단계마다 `PASS`/`FAIL`을 출력하고, 실패하면 에러 라인과 로그 끝부분을 함께 출력한다. 전체 로그는 `.harness/logs/`에 남는다.
   - 출력만으로 원인을 알 수 없으면 출력에 나온 로그 파일을 Read로 읽는다.
   - 출력에 `lint --fix로 바뀐 파일`이 있으면 변경 파일 목록에 포함한다.
2. `code-reviewer` 서브에이전트에 설계 문서 경로, 변경 파일 목록, **1의 스크립트 출력**을 넘겨 리뷰를 맡긴다. reviewer는 검증 명령을 다시 실행하지 않는다.
3. 검증이 실패하면 implementer에 스크립트 출력(실패 요약과 로그 경로)을 넘겨 수정시킨다. 수정은 최대 2회까지 하며, 그래도 실패하면 P0으로 보고한다.
4. implementer가 보고한 `설계 이탈` 중 비즈니스 규칙이 바뀐 것이 있으면 `docs/domain/`과 설계 문서의 `도메인 지식 변경` 표를 실제 구현에 맞게 고치고 보고서의 `도메인 문서` 절에 적는다.

## [단계 9] P 단계 결과 보고

code-reviewer는 간단한 보고를 하는 가벼운 모델(haiku)이다. 보고 전에 reviewer가 **P0으로 매긴 항목만** 메인 에이전트가 해당 코드를 직접 확인한다. 오판이면 등급을 고치거나 뺀다. P1·P2는 reviewer 결과를 그대로 쓴다.

`.claude/skills/develop/templates/report.md` 형식으로 사용자에게 보고한다.

| 등급   | 의미                   | 예                                                                 |
| ------ | ---------------------- | ------------------------------------------------------------------ |
| **P0** | 머지 차단. 반드시 수정 | 빌드·타입·테스트 실패, 요구사항 누락, 버그, 보안 문제, 데이터 손상 |
| **P1** | 머지 전 수정 권장      | 컨벤션(`.claude/rules`) 위반, 누락된 엣지 케이스·테스트, 설계 이탈 |
| **P2** | 개선 제안              | 가독성, 리팩터링, 후속 작업                                        |

## 공통 규칙

- 요구사항 파일이나 대화에 개인정보·인증정보(주민번호, 계좌·카드번호, API 키, 비밀번호, 접속 문자열 등)가 있으면 즉시 중단하고 사내 보안 안내를 따른다. 설계 문서와 코드에도 실제 값 대신 더미 값을 쓴다.
- 서브에이전트에는 대화 맥락이 없다. 프롬프트에 요구사항 원문, 피드백, 설계 문서 경로 등 필요한 것을 모두 담는다.
- 이 하네스는 커밋·PR을 만들지 않는다. 커밋·PR은 개발자가 요청할 때 `.github/commit_convention.md`와 PR 템플릿을 따라 따로 진행한다. `.harness/`, `docs/`, `.claude/`, `CLAUDE.md`는 로컬 전용이므로 스테이징하지 않는다.
