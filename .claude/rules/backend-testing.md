# 백엔드 테스트 코드 컨벤션

`apps/api`(NestJS)에서 테스트를 작성하거나 고칠 때는 아래 규칙을 따른다.
프로덕션 코드 설계 규칙(계층, 팩터리 메서드, 포트 등)은 `.claude/rules/backend-conventions.md`를 따른다.
테스트 러너는 NestJS 기본 구성인 Jest(ts-jest)와 supertest를 기준으로 한다.

> 규칙 이전에 작성된 테스트(예: `describe('RoomTest')`, `Object.create`로 만든 given, Repository를 `jest.fn()`으로 대체한 통합 테스트)는 작업 범위 밖에서 고치지 않는다. 새로 쓰거나 수정하는 테스트에 이 규칙을 적용한다.

## 1. 무엇을, 어느 계층에서 테스트하는가

테스트는 **깨졌을 때 "어떤 비즈니스 규칙이 깨졌다"고 말할 수 있는 것**만 쓴다. 그 문장을 말할 수 없는 테스트는 쓰지 않는다.

- 테스트 개수와 커버리지는 목표가 아니다. 테스트도 유지보수할 코드다. 리팩터링할 때마다 함께 고쳐야 하지만 버그는 잡지 못하는 테스트는 비용일 뿐이다.
- 비즈니스 규칙이 적은 기능은 테스트도 적은 것이 정상이다. 계층을 채우려고 테스트를 만들지 않는다.

### 1-1. 쓰는 테스트

| 대상                        | 예                                                                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 코드가 판단하는 도메인 규칙 | 상태 전이 가능 여부(배송 시작 후 취소 불가), 계산(할인 금액), 같은 행위 반복 시 결과(멱등성)                 |
| 틀리기 쉬운 경계            | 최대 길이 직전·직후, 만료 시각 직전·직후, 정규화(공백·대소문자·유니코드)를 거친 비교                         |
| 영속화와 외부 연동          | 변경 사항이 저장소에 실제로 남는지, 저장된 데이터가 조건대로 조회되는지, 외부 모듈과 주고받는 값과 실패 처리 |
| API 계약                    | 엔드포인트별 성공 응답, 클라이언트가 분기하는 실패 status(404, 409 등)                                       |

### 1-2. 쓰지 않는 테스트

| 쓰지 않는 것                       | 예                                                                                            | 이유                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 프레임워크·라이브러리 동작         | `@IsString` 타입 오류 → 400, `ParseUUIDPipe` → 400, 쿼리 파라미터 중복 → 400                  | 라이브러리가 이미 검증했다. 설정이 적용됐는지만 대표 1건으로 확인한다 |
| 언어와 설계가 보장하는 것          | `readonly` 엔티티의 원본이 바뀌지 않는다, 생성자 값이 필드에 들어간다, getter가 값을 돌려준다 | 깨질 수 있는 판단이 없다                                              |
| 통합 테스트에서 도메인 분기 재검증 | 이미 취소한 주문을 다시 취소하는 분기, 길이 경계를 서비스 통합 테스트에서 다시 확인           | 도메인 단위 테스트가 검증한다. 통합 테스트는 저장·조회·연동만 본다    |
| 다른 계층에서 이미 검증한 규칙     | 이름 길이 규칙을 VO, 엔티티, 서비스, E2E에서 각각 검증                                        | 규칙이 바뀌면 4곳을 고쳐야 하고, 버그는 한 곳에서만 잡힌다            |
| 규칙 없이 자명한 결과              | 저장소가 비면 빈 목록, 삭제하면 목록에서 사라진다                                             | 컬렉션이나 저장소의 기본 동작이다                                     |
| 다른 객체에 그대로 위임하는 메서드 | `order.matches(k)`가 `k.matches(this.name)`만 호출                                            | 위임 대상의 테스트가 이미 검증한다                                    |

### 1-3. 규칙 하나는 한 곳에서 한 번 검증한다

- 규칙은 그 규칙이 **구현된 가장 낮은 계층**에서 검증한다. 대부분은 Domain 단위 테스트다.
- 상위 계층은 같은 규칙을 다시 검증하지 않는다. 도메인 예외가 HTTP status로 이어지는지처럼 **연결**만 대표 1건으로 확인한다.
- 같은 규칙에서 입력만 다른 케이스는 `it`을 늘리지 않고 `it.each` 하나로 묶는다(4절).

### 1-4. 계층별 전략

| 계층                               | 언제 쓰나                                                                                                                                                                              | 테스트 종류                 | 파일                                                |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- | --------------------------------------------------- |
| Domain (entity, VO, 도메인 서비스) | 판단하는 규칙이 있으면 쓴다. **테스트 대부분은 여기에 있어야 한다**                                                                                                                    | 단위                        | `test/<모듈>/domain/<대상>.spec.ts`                 |
| Service                            | 상태를 바꾸는 유스케이스는 **변경이 저장소에 남는지** 1건. 조회 유스케이스는 저장된 데이터가 **조건대로 조회되는지**. 외부 시스템 연동과 실패 처리, 트랜잭션 롤백이 있으면 그것도 쓴다 | 통합 (실제 Repository 구현) | `test/<모듈>/service/<대상>.integration.spec.ts`    |
| Repository                         | 직접 작성한 조건 조회나 커스텀 쿼리, 정렬처럼 저장소가 도메인 규칙을 책임질 때만 쓴다                                                                                                  | 통합                        | `test/<모듈>/repository/<대상>.integration.spec.ts` |
| Controller                         | 엔드포인트마다 성공 1건. 실패 status는 **서로 다른 코드 경로**마다 1건. 프레임워크 검증 설정은 대표 1건                                                                                | E2E (블랙박스, supertest)   | `test/<모듈>/controller/<대상>.controller.spec.ts`  |

모든 테스트는 `apps/api/test/` 아래에 두고, **`src/`의 경로를 그대로 따른다**(모듈 → 계층 → 파일). 종류별 최상위 폴더(`unit/`, `integration/`, `e2e/`)는 만들지 않는다. `src/`에는 테스트 파일을 두지 않는다.

```
apps/api/test/
├── health/health.controller.spec.ts                      # src/health/health.controller.ts
├── music/service/music-query.service.integration.spec.ts # src/music/service/music-query.service.ts
└── pomodoro/
    ├── domain/room.entity.spec.ts                        # src/pomodoro/domain/room.entity.ts
    ├── service/enter-room.service.integration.spec.ts    # 서비스마다 파일 하나. 저장·조회·연동만 검증
    └── controller/pomodoro.controller.spec.ts            # supertest로 HTTP 요청·응답만 검증
```

- 파일 이름은 대상 파일 이름에 접미사를 붙인다. 단위·E2E는 `.spec.ts`(`room.entity.ts` → `room.entity.spec.ts`), 통합은 `.integration.spec.ts`.
- 테스트 대상은 `../../../src/<모듈>/<계층>/...` 상대 경로로 import한다. `@pomodoro/shared`는 Jest `moduleNameMapper`가 shared `src`로 연결한다.
- 모든 테스트(단위·통합·Controller)는 `pnpm --filter @pomodoro/api test`(`testRegex: .*\.spec\.ts$`)로 함께 실행된다. `.e2e-spec.ts` 파일과 `test:e2e` 스크립트는 쓰지 않는다.
- 현재 DB가 없고 저장소는 `InMemory*Repository`다. "실제 DB"는 **실제 Repository 구현체**(InMemory 포함)를 `Test.createTestingModule`에 등록해 쓰는 것을 뜻한다. Repository를 `jest.fn()` 객체로 대체하지 않는다.

### Domain: 단위 테스트

- HTTP, DB, Nest DI 컨테이너 없이 순수 객체만으로 검증한다.
- Mock을 쓰지 않는다. Mock이 필요해진다면 도메인에 외부 의존이 섞인 것이므로 설계부터 의심한다.

### Service: 통합 테스트

- `Test.createTestingModule`로 서비스와 실제 Repository 구현체(현재는 `{ provide: RoomRepository, useClass: InMemoryRoomRepository }`)를 연결해 검증한다. DB가 도입되면 테스트 DB를 연결한다.
- Mock은 우리가 통제할 수 없는 외부 시스템(외부 API, 메일, 메시지 큐 등)에만 쓴다. 같은 앱 안의 Repository나 다른 Service는 Mock하지 않는다.
- 통합 테스트가 검증하는 것은 **도메인 규칙이 아니라 경계**다. 변경이 저장되는가, 저장된 것이 조회되는가, 외부 모듈과 제대로 주고받는가.
  - 상태 변경: 행위 뒤에 저장소에서 **다시 읽어** 바뀐 값이 남았는지 확인한다. 반환값만 보면 저장을 빠뜨린 버그를 잡지 못한다.
  - 조회: 저장소에 데이터를 직접 넣고, 조건(검색어, 필터, 정렬)대로 돌아오는지 확인한다.
  - 실패: 도메인 예외나 외부 시스템 실패가 나면 저장소에 아무것도 남지 않는지(롤백) 확인한다. 트랜잭션이나 여러 번 저장하는 흐름이 있을 때만 쓴다.
- 도메인 메서드의 분기(경계값, 멱등, 상태 전이 불가)는 다시 검증하지 않는다. 대표 입력 하나로 저장·조회 경로만 지난다.
- 검증은 저장소에 남은 최종 상태로 한다. 내부 메서드의 호출 여부(`toHaveBeenCalled`)는 외부 시스템 연동을 확인할 때만 쓴다.

### Repository: 선택적 통합 테스트

- 단순 CRUD는 별도 테스트를 만들지 않는다.
- 조건이 복잡한 조회, QueryBuilder나 Raw SQL을 쓰는 커스텀 쿼리, 저장소가 보장해야 하는 순서만 검증한다.

### Controller: E2E 테스트

- 앱을 띄우고 supertest로 HTTP 요청을 보내 응답(status, body)만 검증한다. 내부 구현은 모른다고 가정한다.
- 응답 계약(status code, body 형태)과 클라이언트가 분기하는 실패 status에 집중한다. 저장 여부는 서비스 통합 테스트가 검증한다.
- 서비스나 도메인 테스트에서 이미 검증한 규칙의 세부 분기를 다시 검증하지 않는다.
- 요청 형식 검증(필수값 누락, 타입 오류, 허용하지 않은 필드)은 ValidationPipe 설정이 적용됐는지 대표 1건만 둔다. 필드마다, 엔드포인트마다 반복하지 않는다.

## 2. 테스트 이름: 테스트는 문서다

테스트 함수명만으로는 테스트의 역할을 충분히 드러낼 수 없다. 테스트의 의도는 `it()` 설명에 섬세하게 담는다.

- `describe`에는 대상 클래스명, 그 아래 `describe`에는 메서드명이나 API(`POST /orders`)를 쓴다.
- `it`은 명사를 나열하지 말고 **완성된 한국어 문장**으로 쓴다.
- 행위만 쓰지 말고 **행위의 결과**까지 쓴다. ("~하면 ~된다", "~할 수 없다")
- 구현 관점의 표현(`특정 시간`, `값`, `실패한다`) 대신 **도메인 용어**(`영업 시작`, `주문 목록`, `생성할 수 없다`)를 쓴다.
- `test1`, `성공`, `실패`, `정상 동작` 같은 모호한 이름은 금지한다.

| ❌ 나쁜 예                                | ✅ 좋은 예                               | 고친 점                           |
| ----------------------------------------- | ---------------------------------------- | --------------------------------- |
| 음료 1개 추가 테스트                      | 음료 1개를 추가하면 주문 목록에 담긴다   | 명사 나열을 문장으로, 결과를 추가 |
| 특정 시간 이전에 주문을 생성하면 실패한다 | 영업 시작 이전에는 주문을 생성할 수 없다 | 구현 표현을 도메인 용어로 바꿈    |
| 주문 취소 실패                            | 배송이 시작된 주문은 취소할 수 없다      | 조건과 도메인 규칙을 드러냄       |

```ts
describe('Order', () => {
  describe('addBeverage', () => {
    it('음료 1개를 추가하면 주문 목록에 담긴다', () => {});
  });
});

describe('CreateOrderService', () => {
  describe('createOrder', () => {
    it('영업 시작 이전에는 주문을 생성할 수 없다', () => {});
  });
});
```

## 3. given / when / then 구조

- 모든 테스트 본문을 `// given`, `// when`, `// then` 주석으로 나눈다. 준비할 것이 없으면 `// given`은 생략한다.
- `when`에서는 검증 대상 행위 **하나만** 실행한다.
- 예외 검증처럼 when과 then이 붙는 경우 `// when & then`으로 합친다.

```ts
it('결제 완료된 주문을 취소하면 주문 상태가 CANCELED로 바뀐다', () => {
  // given
  const order = Order.restore({
    id: 1,
    status: OrderStatus.PAID,
    totalPrice: 10_000,
  });

  // when
  order.cancel();

  // then
  expect(order.status).toBe(OrderStatus.CANCELED);
});
```

## 4. 테스트 하나에는 주제 하나

- 테스트 하나는 행동(규칙) 하나만 검증한다.
- 테스트 본문에 `for`, `forEach`, `if`, `switch`를 쓰지 않는다. 케이스가 여러 개면 `it`을 나눈다.
- 같은 규칙을 입력값만 바꿔 검증할 때는 `it`을 여러 개 만들지 않고 `it.each`로 묶는다. 템플릿 이름(`'$status 상태의 주문은 취소할 수 없다'`)이 규칙을 그대로 설명해야 한다. 기대 결과가 케이스마다 다르면 나눈다.

## 5. 결정론적 테스트

- 검증 대상 코드 안에서 `new Date()`, `Date.now()`, `Math.random()`, `randomUUID()`를 직접 호출하지 않는다.
- 현재 시각과 난수는 **매개변수로 주입**받도록 프로덕션 코드를 설계하고, 테스트에서는 고정값을 넘긴다.
- 매개변수 주입이 어려운 계층(Service)에서는 `Clock`처럼 주입 가능한 provider를 두고 테스트 모듈에서 고정값 구현으로 교체한다.
- `jest.useFakeTimers()`는 타이머(`setTimeout` 등) 동작 검증에만 쓴다. 시각 고정 용도로 남용하지 않는다.

```ts
// ❌ 실행 시점에 따라 결과가 달라진다
isExpired(): boolean {
  return this.expiredAt < new Date();
}

// ✅ 현재 시각을 주입받는다
isExpired(now: Date): boolean {
  return this.expiredAt < now;
}

it('만료 시각이 지난 쿠폰은 만료 상태다', () => {
  // given
  const coupon = Coupon.restore({ expiredAt: new Date('2026-01-01T00:00:00Z') });

  // when
  const expired = coupon.isExpired(new Date('2026-01-02T00:00:00Z'));

  // then
  expect(expired).toBe(true);
});
```

## 6. given은 순수한 데이터 준비 구간

- `given`에서 팩토리 메서드나 비즈니스 메서드를 호출해 상태를 만들지 않는다. given에서 실패하면 원인이 given인지 when인지 알 수 없다.
- 도메인 규칙을 검증하는 팩터리(`create`, `of`, `from`)도 given에서 쓰지 않는다.
- 검증 없이 상태를 되살리는 `restore`나 이를 감싼 테스트용 빌더로 원하는 상태를 **직접** 만든다(backend-conventions 4절).
- 테스트 대상 엔티티에 `restore`가 없으면(기존 `Room`, `Participant` 등) 그 작업에서 `restore`를 추가해 쓴다. `Object.create` + `Object.assign`으로 private 필드를 채우는 방식은 새 테스트에서 쓰지 않는다.
- 팩터리의 검증 자체(`of`의 불변식, `create`의 생성 시점 규칙)를 테스트할 때는 팩터리 호출이 `when`이다.
- 통합 테스트에서도 다른 Service 메서드를 호출하지 말고 Repository로 데이터를 직접 저장한다.

```ts
// ❌ given에서 비즈니스 메서드로 상태를 만든다
const order = Order.create({ id: 'order-1', items, now, businessHours });
order.pay();
order.startDelivery();

// ✅ 원하는 상태를 직접 만든다
const order = Order.restore({
  id: 'order-1',
  status: OrderStatus.DELIVERING,
  items,
  orderedAt,
});
```

## 7. 테스트 간 독립성

- 각 테스트는 자기가 쓸 데이터를 스스로 준비한다. 여러 테스트가 하나의 객체나 DB 레코드를 공유하지 않는다.
- 파일 최상단의 `let` 변수에 테스트 데이터를 담아 여러 테스트에서 재사용하지 않는다.
- 실행 순서나 단독 실행(`it.only`) 여부와 관계없이 같은 결과가 나와야 한다.
- 통합·E2E 테스트는 테스트마다 저장소를 초기화한다. InMemory 저장소는 `beforeEach`에서 테스트 모듈을 새로 만들어 초기화하고, DB 도입 후에는 truncate 또는 트랜잭션 롤백을 쓴다.

## 8. beforeEach는 지양

- 테스트 데이터 준비를 `beforeEach`로 모으지 않는다. 데이터는 각 테스트의 `given`에 둔다.
- 테스트를 이해하려고 `beforeEach`와 본문을 오가야 한다면 잘못 쓴 것이다.
- 예외: 테스트 내용을 읽는 데 필요 없고, 바꿔도 개별 테스트의 의미에 영향을 주지 않는 **인프라 설정**은 허용한다.
  - 예: Nest 앱·테스트 모듈 생성(`beforeAll`), DB 초기화, `jest.clearAllMocks()`

## 9. 작성 순서

새 기능의 테스트는 아래 순서로 작성한다. 각 단계에서 1절 기준에 맞는 테스트가 없으면 그 단계는 건너뛴다.

1. 도메인 문서(`docs/domain/`)에서 이번 기능의 규칙을 고르고, 규칙마다 "깨지면 무엇이 잘못되는가"를 한 문장으로 적는다. 문장을 적을 수 없는 규칙은 테스트하지 않는다.
2. Domain 단위 테스트: 1에서 고른 규칙
3. Service 통합 테스트: 유스케이스마다 변경이 저장되는지, 조건대로 조회되는지, 외부 연동이 되는지. Repository 통합 테스트는 1-4의 조건에 해당할 때만
4. Controller E2E 테스트: 엔드포인트별 성공 응답과 클라이언트가 분기하는 실패 status

## 10. 작성 후 체크리스트

- [ ] 테스트마다 "깨지면 어떤 비즈니스 규칙이 깨진 것인가"를 한 문장으로 말할 수 있는가 (1절)
- [ ] 프레임워크·언어가 보장하는 동작이나 다른 객체에 위임만 하는 도메인 메서드를 테스트하지 않았는가 (1-2)
- [ ] 같은 규칙을 여러 계층에서 반복 검증하지 않았는가 (1-3)
- [ ] 상태를 바꾸는 서비스는 저장소에서 다시 읽어 변경이 남았는지 확인했는가 (1-4)
- [ ] 통합 테스트가 도메인 분기를 다시 검증하지 않고 저장·조회·연동만 보는가 (1-2, 1-4)
- [ ] `it` 이름이 조건과 결과를 담은 완성된 문장인가
- [ ] given / when / then이 나뉘어 있고 when이 행위 하나인가
- [ ] 반복문이나 분기 없이 테스트 하나가 규칙 하나만 검증하는가
- [ ] 현재 시각이나 난수에 의존하지 않는가
- [ ] given에서 비즈니스 메서드나 `create`/`of`/`from`을 호출하지 않고 `restore`로 만들었는가
- [ ] 다른 테스트와 데이터를 공유하지 않는가
- [ ] 테스트 데이터를 `beforeEach`에 숨기지 않았는가
